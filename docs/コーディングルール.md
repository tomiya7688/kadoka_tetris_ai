# コーディングルール

## 基本
Pythonを使用し、UTF-8・インデント4スペースとする。
モジュール・関数・変数は snake_case、クラスは PascalCase、定数は UPPER_SNAKE_CASE。
公開関数に型注釈を付け、理由や制約が必要な箇所に短いコメントを書く。

1クラスにつき1ファイル、1クラスにつき1責務、1関数につき1処理。
独立した複数の処理は名前を付けて分ける。不要な抽象化は追加しない。

性能上のhot pathでは、実測または明確な複雑度上の理由がある場合に限り局所的な例外を許可する。inner loopを細かく分割することでallocationやcall overheadが増える場合などは、公開責務境界を維持したまま最適化してよい。

## 境界
- core は GUI、キーボード、ファイル、実時計に依存しない。
- canonicalなゲーム状態はcore/applicationの権威ある状態遷移が所有する。
- AIは読み取り用の観測を受け取り、意味的コマンドを返す。実盤面を書き換えない。
- AI出力は提案であり、人間入力と同じ検証・状態遷移を通す。
- gameplay/runtime は benchmark、training、dataset conversion、rich analysis に依存しない。これらは上位toolingとしてruntimeを利用する。
- 人間とAIの操作は共通の検証・状態遷移を通す。
- 乱数生成器とseedは明示的に渡し、グローバル乱数へ依存しない。
- ゲーム進行は整数tickで管理し、表示FPSに依存させない。
- 調整値はJSON設定へ置き、読み込み時に型・範囲・未知キーを検証する。
- 不正な外部入力は理由付きで拒否する。例外を握り潰さない。

## AI・探索
- correctness before strength。強い/速いAIより、正しい状態・正しい観測・再現可能な比較を優先する。
- AIへ未公開の将来ツモや内部乱数状態を渡さない。
- 同じ意味のAI/human actionに別ルールを作らない。
- AI改善は同じseed群、同じ設定、同じ入力制約で比較する。
- 評価・探索のhot pathは必要ならデータ指向・cache・まとめ計算を許可するが、core/runtime/toolingの依存方向は崩さない。

## 検証と変更管理
標準 unittest を基本とし、コアとAIはGUIなしで検証できるようにする。
衝突、回転、消去、ツモ、ゲームオーバー、コマンド検証、再現性を優先する。

変更範囲のテストを先に実行し、必要に応じ全体テスト・構文検証を行う。
architecture boundaryは `python tools/kadoka_rule_checker.py .` で確認する。
Git管理開始後は git diff --check も確認する。
機能単位でコミットし、ブランチとGitHub更新はAGENTS.mdおよび開発予定に従う。

配布に影響する変更では、source testsだけで完了とせず `build.bat` で実配布物を生成し、`tools/distribution/smoke_test.py` のartifact-level evidenceを取る。

CI/build/release、AI共通I/F、Runtime/tooling境界、benchmark、model/package、checkerを大きく変える時は `docs/sibling-project-alignment.md` を参照し、Kadoka Othello AI / Kadoka Shougi AIの現行手法も短く確認する。
