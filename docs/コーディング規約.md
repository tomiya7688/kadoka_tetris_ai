# コーディング規約

この文書はKadoka Tetris AIで新規作成・変更するコードの必須基準です。Pull Requestでは [レビュー基準](レビュー基準.md) に沿って確認します。読みやすさと安全性を優先し、例外を設ける場合は理由と影響範囲を差分または設計書に記録してください。

## 文章と名前

- コード、コメント、説明文は、文として読める日本語またはプロジェクト内で統一した英語で書いてください。意味が曖昧な断片、文脈のない略語、読み手が補完しないと分からない文を残してはいけません。
- 関数・クラス・変数名は、名前だけで役割と対象が分かる語を選んでください。`data`、`value`、`thing`、`do_work` のように対象・動作が見えない名前や、一般的でない省略形を避けてください。
- 真偽値は `is_`、`has_`、`can_` など状態を読み取れる名前にしてください。数・範囲・単位は名前に含めてください（例: `player_count`、`timeout_seconds`）。
- コード上の名前付けはPythonでsnake_case、クラスでPascalCase、定数でUPPER_SNAKE_CASEを使います。C++は既存の標準と同じ対象内で一貫させます。

ソースと文書はUTF-8で保存してください。Pythonはインデント4スペース、公開関数・メソッドには型注釈を付けてください。C++では対象targetの既存format・警告設定に従い、所有権を見えにくくする生ポインタ所有を避けてください。

## 責務と処理の分割

- ひとつのクラスはひとつの責務を持たせてください。状態、ライフサイクル、不変条件を複数の関数が共同で管理するまとまりには、その状態を所有するクラスを設けてください。
- ひとつの関数はひとつの処理単位を担当させてください。入力検証、変換、永続化、状態変更など異なる責務を一つの関数へ詰め込まず、意味のある名前を付けて分けてください。
- 関連する状態や処理を複数の場所へ分散させず、責任を持つクラス・モジュールにまとめてください。単独の処理に形式だけのクラスを追加せず、所有する状態や不変条件が明確な単位をクラス化してください。
- 一つのファイルには原則として一つの主要クラスを置きます。異なる責務のクラスや関数群が集まり、必要な部分だけを理解・変更・検証しにくくなったらファイルを分割してください。
- 同じ処理や条件を複製せず、共通の責任箇所へまとめてください。抽象化は具体的な重複や拡張要求を解決する場合に限ります。

## 宣言コメントと処理コメント

クラス、公開関数、公開メソッドの宣言直前には、[JSON-like Comment Outs](https://github.com/tomiya7688/Json-like-comment-outs) の構造化コメントを付けてください。コメント本文とキーは日本語で統一できます。厳密なJSONやXMLへの変換は要求しません。

クラスの例:

```text
{
  責務: [
    NativeRuntime: Python学習toolingからC++ Runtimeを所有・操作する
  ]
  フィールド: [
    _handle: C++ Runtimeのopaque handle
    _player_count: Runtimeが管理するplayer数
  ]
  処理: [
    1: Runtimeを生成して所有する
    2: 可視Observationとsemantic proposalを橋渡しする
    3: close時にnative handleを一度だけ解放する
  ]
}
```

関数・メソッドの例:

```text
{
  責務: [
    submit_many: 1 tick分のplayer proposalを一括登録する
  ]
  処理: [
    1: player、sequence、actionを検証する
    2: C++ Runtimeへbatchを一度に渡す
    3: 検証失敗を呼び出し元へ返す
  ]
  引数: [
    tick: 登録対象tick
    proposals: player、開始sequence、semantic actionの列
  ]
  戻り値: 登録結果
  エラー: 範囲外入力、重複sequence、過去tickを拒否する
}
```

- 宣言コメントには、責務、主な処理、入力と出力、重要な失敗条件を対象に応じて書いてください。クラスでは主要な保持状態も説明してください。
- 実装内部では、ひとつの意味ある処理単位ごとに通常コメントを置いてください。コメントはコードの逐語的な言い換えではなく、目的、理由、不変条件、注意点を説明してください。単純な代入を一行ずつ説明するコメントは書かないでください。
- コメントは実装と一致させ、処理や状態の意味が変わったら同じ差分で更新してください。コメントとコードが矛盾する状態を残してはいけません。
- JSON-like Comment Outsは宣言レベルに使い、ローカル変数・分岐・実装内部には通常コメントを使ってください。意味・必須項目の基準は参照仕様の日本語版に従います。

## 正しさ、安全性、性能

- バグを招く未検証前提、境界値漏れ、整数overflow、無効参照、競合状態、部分更新、握り潰した例外を残してはいけません。外部入力は範囲・形式を検証し、失敗時の状態変化を明確にしてください。
- 予測できる入力規模に対して妥当なアルゴリズムを選んでください。意図しない二重ループ、繰り返し検索、全件コピー、再計算を避けてください。計算量とメモリ量が問題になる処理は、規模と上限を設計またはコメントで説明してください。
- gameplay/runtimeの実行性能を損なう不要なallocation、copy、I/O、lock、FFI呼び出しを追加してはいけません。hot pathを変更する場合は対象workloadを測定し、seed・設定・実行数を揃えた比較結果を添えてください。
- hot pathを細かく関数分割するとallocationやcall overheadが増える場合は、測定値または計算量上の理由を示したうえで局所的な例外を認めます。公開責務境界や検証しやすさは維持してください。
- 危険なファイル操作、process起動、外部入力の解釈、raw pointer、手動メモリ管理は必要最小限にしてください。サイズ・所有権・解放条件・失敗経路を明確にし、C++はRAIIと既存のmemory-safety CIを利用してください。
- 拡張点は、追加する利用者・データ・動作と既存契約への影響が説明できる形にしてください。未知の設定値を黙って受け入れる、振る舞いを複数箇所へ直書きするなど、変更時に同期箇所が分からなくなる実装を避けてください。
- authoritative gameplay/core/runtimeはC++が所有します。Pythonは学習・dataset・評価・実験等のtoolingに使い、C++ CoreからPythonへ依存させません。AIはproposalを返し、canonical stateを直接変更しません。
- CoreはGUI、keyboard、filesystem、実時計に依存させません。人間とAIは同じsemantic commandと権威ある検証・状態遷移を使います。seedと整数tickを明示し、グローバル乱数と表示FPSに依存させません。
- 未公開の将来ツモや内部乱数状態をAIへ渡してはいけません。gameplay/runtimeからbenchmark、training、dataset解析へ逆依存させません。
- 設定値は読み込み時に型・範囲・未知keyを検証し、不正な外部入力は理由を示して拒否してください。例外を握り潰してはいけません。

## テストとCI

- 変更した責務に対する自動テストを追加または更新し、正常系、境界値、失敗経路、再現性を確認してください。テストしにくい構造は責務や依存関係を見直してください。
- 対象routeのchecker・targeted testsを通し、通常のCIを通過する状態にしてください。C++ Core/RuntimeはCMake buildとCTest、Python toolingはcompileall・Ruff・unittestを基本にします。
- E2Eで失敗する変更を通してはいけません。GUI、配布、実環境を変更する場合は対象のE2Eまたはartifact smoke evidenceも確認してください。実施していない検証を成功したと報告してはいけません。
- ローカルで環境制約があり全検証できない場合は、失敗したコマンド、原因、CIで確認する範囲を報告してください。

## ドキュメント

- 設計書・仕様書は、読者が目的と必要な操作を一読でつかめる文章にしてください。用語を定義し、文の主語と述語を明確にしてください。
- 利用者が主語の手順は「〜してください」、アプリケーションが主語の動作は「〜します」「〜になります」と書いてください。主語に合わない語尾や、誰が行うか不明な受け身を避けてください。
- 機能説明には背景、目的、手段、利用者が実行する方法を含めてください。操作手順では編集・保存・入力・実行・期待結果を具体的に書いてください。
- 軽い設計は `docs/設計書.md`、詳細は `docs/機能名/機能説明書.md` の構成に従ってください。表はMarkdown、図はMermaidを使います。
