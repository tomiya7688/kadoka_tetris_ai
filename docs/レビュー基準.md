# レビュー基準

この基準はコード、テスト、設計書、利用者向け説明、CI変更に適用します。項目に違反する差分は修正されるまで承認してはいけません。違反を避けられない制約がある場合は、理由、影響、代替策を差分に記録し、レビューで解決方法を決めてください。

## 読みやすさ

- 説明文・コメント・コードが、文や処理として読めること。曖昧な断片、文法が崩れた説明、前提を読み手に推測させる書き方を残さない。
- 関数名、クラス名、変数名から「何を対象に、何をするか」がすぐ分かること。意味の薄い名前、場当たり的な略語、スコープ外でも衝突しやすい名前を残さない。
- 一つのクラスに複数の責務を持たせない。一つの関数に複数の独立した処理単位を持たせない。状態と、その状態を維持する処理は責任を持つまとまりへ集める。
- 責務を追いにくい長いファイルを残さない。ファイル行数だけでなく、複数の主要責務、変更理由、テスト境界が一つの場所へ混在していないかを確認する。
- 意味ある処理単位にコメントがあり、目的・理由・不変条件が分かること。コードの逐語的な説明だけのコメントや、実装と食い違うコメントを残さない。
- クラス・公開関数・公開メソッドの宣言コメントがJSON-like Comment Outsの構造に沿っていること。キー名は日本語でよく、クラスは責務・主要フィールド・処理、関数は責務・処理・引数・戻り値を記述する。内部コメントは通常コメントを使う。
- 重複した処理、条件、設定値、説明を増やさない。削除や共通化で読解負担を下げられる冗長なコードを残さない。

## 正しさと安全性

- バグを生む可能性のある未検証前提、境界値漏れ、overflow、状態の部分更新、例外の握り潰し、所有権の不備、競合状態がないこと。
- 外部入力、ファイルpath、process、raw memory、C ABIなどの危険な操作が必要最小限で、入力検証・上限・権限・解放経路が確認できること。
- authoritative stateの所有者と依存方向が守られていること。Tetrisのgameplay/core/runtimeはC++が正本であり、Python AIは観測からproposalを返し、C++ Runtimeの検証を通すこと。
- AIやbenchmarkがツモ制約、seed、設定、入力制約を守り、比較可能な条件とbounded runtimeを示すこと。

## 性能と拡張性

- データ規模と実行頻度に見合うアルゴリズムを使い、意図しない高計算量や不要な全件走査・copy・allocationがないこと。
- 実行性能に影響する変更では、影響するhot pathと同条件の測定結果があり、回帰が説明・解決されていること。
- 将来の追加時に変更箇所や契約が追えること。分岐条件、設定値、依存関係、エラー処理が場当たり的に散らばっていないこと。
- 抽象化は責務の分離や実際の拡張点を明確にし、単に間接層やファイルを増やすだけになっていないこと。

## テスト、CI、E2E

- 変更の正常系・失敗系・境界値を確認するテストがあり、通常のCIを通過すること。
- 必要なC++ build/CTest、Python compileall/Ruff/unittest、checkerが実行されていること。
- 起動、操作、設定、配布に影響する変更では適切なE2Eまたはartifact smokeを通過すること。E2Eで再現する不具合を残さないこと。
- CIやE2Eで未確認の範囲を明記し、実施していない検証を通過済みと扱わないこと。

## 仕様書と利用者向け説明

- 人間が読み進められる自然な日本語で、対象読者、用語、前提が明確であること。
- 利用者が主語なら依頼形の「してください」、アプリケーションが主語なら「します」「なります」を使い、主語と述語を対応させること。
- 背景、目的、実現手段、利用者の実行方法が揃っていること。手順には必要な編集・保存・入力・実行方法と期待結果が書かれていること。
- 実装済み、計画中、未決定の内容を混同せず、コード・テストと矛盾しないこと。

## 判定

上記のいずれかに違反する場合は、該当箇所、利用者または保守への影響、必要な修正を具体的に示し、承認を保留してください。軽微な指摘も理由を添えて記録し、無言で見逃さないでください。
